# Agent 失控：它会跑偏，而且不会自己停

> 检索日期：2026-09-09
> **状态：待审查**（案例来自公开 post-mortem 与媒体报道，数字请以原始来源为准）

## 一、头号案例：两个 Agent 聊了 11 天，烧掉 4.7 万美元

- **事件**：2025 年 11 月，一个基于 LangChain、走 A2A 协议的四 Agent 市场研究流程中，「Analyzer」与「Verifier」两个 Agent 陷入互相请求的无终止循环，**持续 264 小时（11 天）无人发现**。
- **发现方式**：不是系统内部报警，而是**账单看板阈值触发**——此时已产生约 **$47,000** API 费用。公开复盘发表于 2026 年 3 月。
- **根因**：Verifier 从不批准、也从不给出**有边界的**澄清要求，只是一直要求"再分析一下"；Analyzer 一直照做。整个流程**没有终止条件、没有最大迭代次数、没有单 Agent 预算**。
- **最扎心的一句复盘**：**"他们有可观测性，但没有强制力。"**（the team had observability, they did not have enforcement）
- 来源：https://www.decryptiondigest.com/blog/ai-agent-runaway-api-cost-overrun-troubleshooting

## 三、机制解释（为什么是必然，不是意外）

1. **"有帮助"的本能就是循环的燃料**：让一个模型判断"输出是否完成"，只要没有**刚性的评分标准和阈值**，它几乎总能再想到一个"还值得考虑的角度"。于是永远不批。
2. **传统程序抛异常就停；Agent 遇到错会重试、反思、再重试**。没有终止条件，它根本不知道什么时候该放弃。
3. **判断标准必须由非模型的东西来定**：凡是一个 Agent 的输出交给另一个 Agent 去评判、而"完成"的定义不是可判定的，这种失败模式就潜伏在其中。

## 四、教学转述（讲师参考）

- Agent 最危险的不是**做错**，是**它自认为做完了**——或者反过来，永远不认为做完了。
- 所以给 Agent 派活，必须三件套齐全：**终止条件 + 最大步数 + 预算上限**。
- 一句可上屏的对比：**"传统程序抛异常就停；Agent 遇错会重试、反思、再重试。"**
- 收口金句（备用）：**"先有刹车，再谈自主。"**

## 使用限制

- 「米哈游 13 小时 200 万」「亚马逊 5 个月 180 万美元」等说法流传较广但来源为视频转写，**可靠性不足，不建议上屏**，仅作讲师自己理解用。
- 面向非技术岗学员，**重点讲行为后果（跑不停、账单失控、删了数据）和人该设的刹车**，不讲 A2A、LangChain、API 这些名词。

## 备用弹药（学员追问时才给）

> 学员问"那是不是多装几个监控就行？"——答：那个 11 天的案例里，团队是有监控仪表盘的，但账单告警一天只更新三次，而循环一秒跑一圈。复盘原话是"我们有可观测性，却没有执行前的强制刹车"。所以**刹车要装在动作发生之前，不是之后**。
